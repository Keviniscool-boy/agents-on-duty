# 售后演示业务

当前是基于 SQLite 的单机演示，不连接真实订单或支付系统。每个登录用户首次查看订单时会生成各自的演示订单；数据保存在 `data/after_sales.sqlite3`，不同账号的订单互不可见。演示数据库与账户数据库需要一起持久化；删除后会重新生成演示数据。

## 业务规则与状态

- 已签收且签收时间不超过 7 天的订单可以提交申请。取消或未签收的订单、超期订单会被拒绝。
- 知识库政策还要求商品未使用、包装完整；这两项无法由演示数据确认，所有符合初筛条件的申请均进入人工审核，不能声称已批准或已退款。
- 每张订单最多有一个待审核申请。申请和关联工单在同一事务中创建；退款申请初始为 `pending_review`，工单为 `pending`。
- 用户可以撤回自己的待审核申请，申请和工单同时变为 `cancelled`；撤回后可以发起新的申请。批准、拒绝、执行退款及相应的工单流转属于后续人工客服阶段，目前没有实现。

## 身份和接口

接口需要登录，用户身份来自服务端验证的登录态，不采用请求体中的用户 ID。订单和退款申请不存在或不属于当前用户时，返回相同的 404，避免泄露其他账户的数据。

| 方法与路径 | 用途 |
|---|---|
| `GET /api/orders` | 查看自己的演示订单 |
| `GET /api/orders/{order_id}` | 查看自己的订单 |
| `GET /api/refunds` | 查看自己的申请及关联工单号 |
| `POST /api/refunds` | 申请退款，JSON 字段为 `order_id` 和 `reason` |
| `POST /api/refunds/{refund_id}/cancel` | 撤回待审核申请 |

申请接口必须带 `Idempotency-Key` 请求头。一次逻辑请求的重试应使用同一个键；同一用户以相同键和内容重试会返回原申请的当前状态，相同键对应不同内容返回 409。撤回后的旧请求重试不会创建新申请；用户主动重新申请时需使用新键。同订单已有待审核申请时，相同原因会关联到该申请，不同原因返回 409。

业务错误包含 `error` 和 `message`：订单或申请无权访问返回 404，幂等键冲突、已有不同原因的申请或不可撤回状态返回 409，参数无效或不符合演示规则返回 400。MCP 和本地备用路径复用相同业务逻辑；内部 MCP 服务依赖调用方提供可信用户身份，不能直接暴露给不可信客户端。

## 当前边界

- 尚无客服账号、审批界面、Agent 中断恢复、真实退款或支付对账。
- SQLite 和模拟订单适合单机演示；没有多实例业务数据库、完整审计或生产级权限体系。
- 申请的独立幂等键用于防止重试导致重复申请，不代表未来支付渠道的退款执行已经具备幂等保障。
