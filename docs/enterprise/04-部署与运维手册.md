# 04 · 部署与运维手册

版本 1.0.0 · 2026-11-04 · 环境：docker compose 单机四容器

## 1. 前置条件

- Docker + docker compose v2
- `.env`（仓库根目录，**不入库**）必需项（只列变量名，值由部署方提供）：

| 变量 | 用途 | 缺失后果 |
|---|---|---|
| `JWT_SECRET_KEY` | 令牌签名（≥32 位随机） | **应用拒绝启动** |
| `MYSQL_ROOT_PASSWORD` / `MYSQL_PASSWORD` | 数据库初始化与应用连接 | compose 启动失败 |
| `OPENAI_API_KEY` / `OPENAI_BASE_URL` / `MODEL_NAME` | 聊天与路由模型 | 聊天链路失败（其余功能可用） |
| `DASHSCOPE_API_KEY`（或 OpenAI 兼容 embedding 配置） | 知识索引/检索 | 知识库降级，检索接口 503，Agent 转人工 |
| `MYSQL_USER` / `MYSQL_HOST` / `MYSQL_PORT` / `MYSQL_DATABASE` | 业务兜底存储 | 启动自检失败拒绝启动 |
| `REDIS_URL` | 登录限流与工作记忆 | 降级进程内（功能可用，防护减弱） |
| `COOKIE_SECURE` / `APP_ENV` | 生产 Cookie 策略 | production 下务必 `COOKIE_SECURE=true` |
| `CORS_ALLOW_ORIGINS` | 跨域白名单 | 默认仅本地 8080/5173 |
| `OTEL_EXPORTER_OTLP_ENDPOINT` | 可选 OTLP 上报 | 无后端时日志有连接拒绝噪音，不影响功能 |

## 2. 部署步骤

```bash
# 1) 配置 .env（参照上表；切勿提交到仓库）
# 2) 构建并启动（会重建 app/frontend 镜像；mysql_data 卷持久保留）
docker compose up -d --build
# 3) 健康检查
curl http://localhost:8000/health
curl -o /dev/null -w "%{http_code}" http://localhost:8080/   # 期望 200
# 4) 创建第一个管理员（先在页面注册该用户名，再执行）
docker compose exec app python -m auth.bootstrap_admin <用户名>
# 5) 首次访问 :8080 注册普通账号即可使用
```

> **部署纪律**：前后端必须同批 `--build` 重建。分批更新会产生"旧前端 + 新后端"的
> 混合镜像，表现为功能"凭空消失"（历史教训：工单建出来了但工作台看不到队列 tab）。

## 3. 数据与持久化

| 数据 | 位置 | 备份建议 |
|---|---|---|
| 业务兜底数据 | MySQL 卷 `mysql_data` | 定期 `mysqldump` |
| 账户 / 工单幂等 / 检查点 / 售后 | 宿主机 `./data/*.sqlite3` | 停机窗口拷贝（SQLite 单文件） |
| 知识向量索引 | 宿主机 `./vector_store/` | 随知识库文件一起备份 |
| 会话/工作记忆 | MySQL + Redis（可重建，非权威数据） | 可不备份 |

## 4. 健康检查与监控

- `GET /health`：`healthy / degraded / unknown`；`knowledge_base.status` 说明：
  - `ready` 索引可用；`degraded` embedding 失败（旧索引保留、检索 503）；
  - `empty` 无知识文档；`unknown` 尚未探测（首次检索后变化）。
- 审计与排障：管理员登录 → 管理员工作区 →「运行记录」（按 trace）与「操作审计」；
  或 `GET /api/admin/audit?kind=tool` 等查询。
- 关键告警建议：`/health` 非 healthy、登录 429 激增、审计中 `error_type=mcp_unavailable`
  持续出现（MCP 通道长期降级）。

## 5. 常见故障排查

| 症状 | 排查 | 处置 |
|---|---|---|
| 启动即退出：`JWT_SECRET_KEY 未配置` | `.env` 缺失/为历史默认值 | 设置 ≥32 位随机密钥后重启 |
| 知识问答一律"无法确认" | `/health` 是否 degraded；`.env` embedding 模型名是否有效 | 修正模型名后重启（索引身份不符会自动重建） |
| 检索接口 503 | embedding 服务不可用/额度 | 恢复后自动可用；旧索引不丢 |
| 界面功能"消失" | 前后端镜像版本是否一致 | `docker compose up -d --build` 全量重建 |
| 登录报 429 | 触发限流（60s 内 5 次） | 等待窗口期；检查 Redis 是否可用 |
| 审批后用户侧未收到答复 | 工作台详情 `resume_pending`；审计 kind=tool | 用「重试恢复」端点/按钮重推 |
| OTEL 连接拒绝刷日志 | 未部署 OTLP 后端 | 无影响；关闭 `OTEL_EXPORTER_OTLP_ENDPOINT` 可消除 |

## 6. 升级与回滚

```bash
git fetch && git checkout <tag/commit>
docker compose up -d --build        # 滚动重建（数据卷不受影响）
# 回滚：切回上一 commit 重新 build；SQLite/MySQL 卷不自动迁移，降版本前先备份 ./data
```

- 检查点与幂等库向后兼容由测试守护；跨大版本升级前先跑全量 `pytest`。

## 7. 安全运维清单

- [ ] `.env` 权限 600，不入库、不进镜像（compose `env_file` 仅运行时注入）
- [ ] 生产设置 `APP_ENV=production`（Cookie Secure 强制生效）
- [ ] `CORS_ALLOW_ORIGINS` 收敛到真实域名
- [ ] 定期轮换 `JWT_SECRET_KEY`（轮换后全员重新登录）
- [ ] MySQL 使用最小权限应用账号（默认 `MYSQL_USER=smart_cs_app`，非 root）
- [ ] 备份 `./data` 与 `mysql_data`，并做一次恢复演练
